Random Thoughts on Reproducible Builds

November 22, 2026

micro   programming   trusted-computing

Part of a series of mini thoughts I had while looking into Trusted Computing, a topic I am not too familiar with. The topic for today is on reproducible builds that I shared with my class back on September 22. Reproducible builds have been on my feed since 2024 and it turns out to be an interesting topic and is a trend within the open source community to ensure security, trust and regulatory compliance. Reproducible builds are defined as:

A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts.

In other words, a binary that is reproducible provides users with a way to be certain that the software is genuine and has not been tampered with by reproducing the build themselves or by placing their trust in an independent third party to reproduce the build. The ability for others to compile code given the same source code, build environment and build instructions is important for software longevity. Reproducibility pushes developers to create better documentation and tooling.

As a former Build DevOps developer who inherited a legacy blackbox, it astonished me how bad the state of our legacy product was because we could not physically rebuild artifacts without cloning the VM running on the same machines as before. The lack of expertise and documentation required us to replicate the exact build environment and automation (which contained our build instructions) to even push out a build. Reproducible builds are marketed as a solution for security and compliance but this side effect of enabling others to create the same artifact is powerful.

Of course I am over-exaggerating of the state of the legacy product I worked at in my previous life, it was nonetheless a mess. Anyhow, back to the topic at hand, at the time I shared about reproducible builds, I was contemplating how we could incorporate this idea into trusted computing.

Reproducible builds, at least from what I have seen, are seen through the lens of supply chain attacks and give users a trusted software source (initial integrity) to build on. For instance, if a solution relies on interacting with a crypto library, having the library be reproducible can give us confidence that the library code has not been tampered with. So its hash could be a measurement. The only obvious relevant relation I can think of is to have open source firmware, bootloader, etc. be reproducible so that other manufacturers could rely on the same hash as part of some standardised Reference Integrity Metrics.

There have been efforts by Linux distributions to have the kernel and their packages be reproducible, having achieved 95% or higher reproducibility with Debian having a policy for packages to be reproducibile. The reason I specified firmware and bootloader is because we want our trusted computing base (TCB) to be as small as possible. Yes it would be nice to have reproducible builds on all the libraries relied upon by the OS and critical services, as we do not want to assume trust in the entire OS and its libraries. But if we are able to reproduce the OS, we could be reassured that the OS and its packages have not been tampered with. Though the question of whether we wish to assume trust is a different story, sometimes we have to assume trust depending on what we are working on. In our definition, a component is trusted if it behaves in the expected manner for the intended purpose. This still means a component can be considered trusted even if it contains a security flaw. Also recall that reproducible builds do not guarantee the source code is without flaws, it guarantees independent verification that the resulting binary corresponds to the same source code and build environment.

Rather than trusting the entire OS as that could make the TCB too large, we could chain measurements on top of an anchor (root of trust) and verify step by step the individual components (called the chain of trust). Essentially, at each stage, the previous stage will endorse what is to be loaded next. With the many different hardware configurations that exist, this would be a challenge as there would be too many different measurements to consider.

On a topic of secure boot and TPMs, TPMs are passive devices that are separate from secure boot. TPMs record measurements of what gets loaded and can attest to these measurements but it never blocks anything. Secure boot on the other hand refuses to load any components not signed by a trusted key, verifying the signature of components from the firmware, bootloader, and even potentially up to the kernel modules. Reproducible builds could potentially be used in measurements as one could verify its hashes independently. Secure boot provides provenance (origin) and not reassurance of the contents.
